Ghi chú thiết kế: hapo:docs và reconstruct

File này ghi lại quyết định và suy nghĩ khi triển khai workflow tài liệu trong CafeKit. Phần trọng tâm là dựng tài liệu hệ thống hiện trạng từ source code, đồng thời không làm sơ sài ba nhánh docs chuẩn init, update, summarize.

Quyết định chính

Dùng hapo:docs reconstruct, không tạo skill riêng hapo:reconstruct

Lý do: yêu cầu hiện đã rộng hơn requirement reconstruction. Người dùng muốn dựng tài liệu hệ thống/project docs từ source code, trong đó reconstruct là một mode đặc biệt cho hệ thống hiện hữu hoặc legacy.

  • hapo:docs là namespace đúng cho tài liệu.
  • reconstruct giữ nghĩa as-is/current-state rõ ràng.
  • Sau này có thể thêm init, update, summarize mà không tạo nhiều skill rời rạc.
Đối chiếu Research

Nội dung được kéo từ ~/Research/.claude/skills/docs

Nguồn tham chiếu Điểm giữ lại Điều chỉnh cho CafeKit
init-workflow.md Scout source theo directory thật, tạo baseline docs, kiểm tra LOC sau khi sinh. Đọc docs root từ .claude/runtime.json, dùng hapo:inspect và docs-keeper.
update-workflow.md Scout source change, đọc docs hiện có trước khi sửa, validation sau update. Nhấn mạnh surgical update, giữ .sync_hash chỉ khi docs đã sync thật.
summarize-workflow.md Chỉ cập nhật codebase-summary.md, không quét cả repo nếu user không yêu cầu. Giữ focused scout theo module/path để giảm nhiễu và giảm hallucination.

Bản Research gọi agent docs-manager. Package CafeKit hiện ship agent docs-keeper, nên skill dùng agent đó nhưng giữ nguyên kỷ luật verify-before-write, size check và docs validation.

Command contract

Các lệnh được hỗ trợ

/hapo:docs
/hapo:docs init
/hapo:docs update
/hapo:docs summarize
/hapo:docs reconstruct <scope>

Nếu không có reconstruct, skill xử lý docs bình thường. Nếu prompt có ý legacy/as-is/source-to-docs thì tự chọn reconstruct.

Normal docs

Ba nhánh docs chuẩn không bị gộp sơ sài

Mode Phase chính Output chính
init Preflight → structure scout → evidence scout → docs authoring → size check → validate/sync. Baseline docs như PDR, codebase summary, architecture, standards, roadmap.
update Map source change → đọc docs cũ → surgical edit → size check → validate/sync. Chỉ phần docs bị ảnh hưởng, giữ human-written context còn đúng.
summarize Đọc summary cũ → focused scout → viết summary → validate. codebase-summary.md; không biến thành full documentation run.
Guardrails

Những điều reconstruct không được làm

  • Không thiết kế tương lai.
  • Không thêm requirement mới.
  • Không tạo task hoặc code.
  • Không tạo specs/<feature>.
  • Không claim hiểu đủ business intent chỉ từ code.
  • Không biến phần suy luận thành phần đã quan sát được.
Evidence policy

Phân loại finding

Loại Ý nghĩa Khi dùng
Observed Thấy trực tiếp trong code/test/schema/config. Route, controller, UI flow, enum, validation, test chứng minh rõ.
Inferred Suy luận hợp lý từ nhiều tín hiệu nhưng chưa có bằng chứng end-to-end. Tên file, service, partial flow, integration chưa thấy trigger đầy đủ.
Unknown Chưa đủ bằng chứng. Business intent, manual process, runtime data, external system, code chết.
Reconstruct phases

Luồng reconstruct chi tiết

  1. Scope gate: từ chối kiểu âm thầm dựng cả monolith thành một file; broad scope phải structure scout trước.
  2. Source scout: tìm entry points, UI/routes, schemas, auth checks, jobs, integrations, tests, config.
  3. Evidence ledger: lập từng evidence ID theo surface UI/API/data/auth/job/integration/test/config.
  4. Behavior trace: nối actor, trigger, input, validation, state write, output, errors.
  5. As-is extraction: viết requirement hiện trạng có type, confidence, evidence, exception/gap.
  6. Supporting docs: vai trò, entity/status, business rules, integrations, architecture và unknowns.
  7. Consistency review: đối chiếu requirement với evidence, actors, statuses, integrations và kiến trúc.
  8. Human review gate: chưa approve nếu inferred/unknown quan trọng chưa được người hiểu domain xác nhận.
Best practices áp dụng

Cơ sở thiết kế

  • Docs as Code: tài liệu nằm trong repo và review như code.
  • C4: dùng cho system context/container/component khi cần mô tả kiến trúc.
  • arc42: giữ context, building blocks, runtime behavior, risk, decision.
  • Diataxis: tách explanation/reference/how-to thay vì một file dài.
  • ADR discipline: nếu code hé lộ decision quan trọng thì ghi decision note có evidence, không đoán.
Rủi ro còn lại

Điểm cần kiểm tra khi dùng thực tế

  • Repo legacy lớn cần chia scope. Không nên demo full monolith trong một lượt.
  • Code có thể chứa flow cũ không còn dùng. Human review vẫn bắt buộc.
  • Business rule ngoài code như Excel, email, manual operation sẽ rơi vào Unknown.
  • Nếu muốn sinh diagram đẹp, có thể nối thêm hapo:generate-graph sau khi reconstruct.
Các file đã tác động

Implementation map để double-check

  • skills/docs/SKILL.md: route mode, output contract, evidence rules, agent/tool fit.
  • references/init-workflow.md: baseline docs creation chi tiết.
  • references/update-workflow.md: update docs có source scout, docs-read, surgical edits.
  • references/summarize-workflow.md: summary mode nhỏ và focused.
  • references/reconstruct-workflow.md: evidence ledger và as-is bundle.
  • templates/reconstruction.json và markdown templates: registry, evidence, unknowns có shape rõ.
  • templates/reconstruct-overview.html: review dashboard self-contained cho human mở trực tiếp.
  • validate-docs.cjs: validator docs thường nhận docs root argument để hợp với paths.docs.
  • validate-docs-reconstruct.cjs: validator riêng cho bundle as-is, evidence ID, registry và overview marker.
  • run-skill-self-tests.mjs: test static cho các contract trên.
Review follow-up

Những gap sau self-review đã xử lý

  • Output lỏng: thêm template cho JSON, requirement, evidence, unknowns và HTML overview.
  • Không có deterministic gate: thêm validate-docs-reconstruct.cjs và fixture test valid/invalid.
  • Không có source snapshot: thêm source_revision, source_branch.
  • Không có review state: thêm review_status, reviewed_by, reviewed_at, approved_for_specs.
  • arc42/ADR cover chưa đủ: thêm artifact cho constraints/risks/decisions và glossary.
Handoff

Flow sản phẩm đề xuất

/hapo:docs reconstruct <scope>
→ human review docs/as-is/<scope>
→ /hapo:specs <modernization/change request based on approved as-is docs>
→ /hapo:develop <feature>

Đây là flow bám sát mục tiêu ban đầu: đọc source hệ thống cũ, dựng tài liệu hiện trạng, review, rồi mới tạo spec nâng cấp.
