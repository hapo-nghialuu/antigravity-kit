# Todo App API

この初心者向けの例は、Todoアプリケーション用のREST APIの構築方法を示しています。CafeKit Specのワークフローを学ぶのに最適です。

## 概要

**機能:** TodoリストのREST API
**難易度:** 初心者
**想定時間:** 3〜4時間
**スタック:** Node.js, Express, PostgreSQL

---

## フェーズ 1: 初期化

```bash
/spec-init todo-app-api
```

**初期要件の説明:**
> CRUD操作を備えたTodoアプリケーション用のREST API。ユーザーはTodoを作成、読み取り、更新、削除できる。各Todoにはタイトル、説明、完了ステータス、および優先度（priority level）がある。ステータスおよび優先度によるフィルタリングを含む。

## フェーズ 2: 要件定義

```markdown
# Todo App API - Requirements

## 目的
フィルタリング機能とソート機能を持つ、個人のTodoアイテムを管理するためのREST APIを提供する。

## ターゲットユーザー
- 個人のタスクを管理する一般ユーザー
- このAPIを利用するフロントエンド開発者

## 機能要件

### FR-1: Todoの作成
ユーザーがタイトル付きの新しいTodoを送信した**時**、
システムはTodoアイテムを作成し一意のIDとタイムスタンプとともにそれを返す**こと**。

**受け入れ基準:**
- Title は必須（1〜200文字）
- Description は任意（最大1000文字）
- Priority はデフォルトで "medium"
- Status はデフォルトで "pending"
- Created timestamp は自動生成される

### FR-2: Todoの一覧表示
Todoの一覧をリクエストした**時**、
システムは任意のフィルタリングとソートを備えたページネーション（ページ分割）されたリストを返す**こと**。

**受け入れ基準:**
- Pagination: デフォルトで1ページあたり20件
- Filter by status: pending, in-progress, completed
- Filter by priority: low, medium, high
- Sort by: created_at, priority, title
- Default sort: created_at DESC

### FR-3: Todoの更新
Todoを更新した**時**、
システムは指定されたフィールドを変更し、タイムスタンプを更新する**こと**。

**受け入れ基準:**
- 部分的な更新（Partial updates）をサポートする
- Updated timestamp は自動生成される
- 更新されたTodoを返す
- Todoが見つからない場合は 404

### FR-4: Todoの削除
Todoを削除した**時**、
システムはそれを永久に削除する**こと**。

**受け入れ基準:**
- 成功時は 204 を返す
- Todoが見つからない場合は 404
- 取り消し（Undo）はできない

### FR-5: 完了状態の切り替え（Toggle Completion）
Todoのステータスを切り替えた**時**、
システムは pending と completed の間を切り替える**こと**。

**受け入れ基準:**
- 完了時に completed_at タイムスタンプを設定する
- 再開時（reopened）に completed_at をクリアする
- 利便性のための専用のエンドポイント

## 非機能要件

### パフォーマンス
- API response time < 100ms（リスト操作の場合）
- 100人の同時接続ユーザーをサポート
- ページネーションによって大規模なペイロードを防ぐ

### データの整合性
- Title は空にできない
- Priority は有効な列挙型（enum）の値でなければならない
- Status の遷移（transitions）が有効であること
```

## データベーススキーマ

```sql
CREATE TYPE todo_status AS ENUM ('pending', 'in_progress', 'completed');
CREATE TYPE todo_priority AS ENUM ('low', 'medium', 'high');

CREATE TABLE todos (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title VARCHAR(200) NOT NULL,
  description TEXT,
  status todo_status DEFAULT 'pending',
  priority todo_priority DEFAULT 'medium',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  completed_at TIMESTAMP
);

-- 一般的なクエリのためのインデックス
CREATE INDEX idx_todos_status ON todos(status);
CREATE INDEX idx_todos_priority ON todos(priority);
CREATE INDEX idx_todos_created_at ON todos(created_at DESC);
CREATE INDEX idx_todos_status_priority ON todos(status, priority);
```

## フェーズ 5: 実装のハイライト

### バリデーションスキーマ (Zod)

```typescript
import { z } from 'zod';

export const createTodoSchema = z.object({
  title: z.string().min(1).max(200),
  description: z.string().max(1000).optional(),
  priority: z.enum(['low', 'medium', 'high']).default('medium'),
});

export const updateTodoSchema = createTodoSchema.partial();

export const listTodosQuerySchema = z.object({
  page: z.coerce.number().positive().default(1),
  limit: z.coerce.number().positive().max(100).default(20),
  status: z.enum(['pending', 'in_progress', 'completed']).optional(),
  priority: z.enum(['low', 'medium', 'high']).optional(),
  sort_by: z.enum(['created_at', 'priority', 'title']).default('created_at'),
  order: z.enum(['asc', 'desc']).default('desc'),
});
```

### コントローラーパターン

```typescript
export class TodoController {
  async list(req: Request, res: Response) {
    const query = listTodosQuerySchema.parse(req.query);
    const todos = await TodoModel.findMany(query);
    res.json({
      data: todos.data,
      pagination: todos.pagination,
    });
  }

  async create(req: Request, res: Response) {
    const data = createTodoSchema.parse(req.body);
    const todo = await TodoModel.create(data);
    res.status(201).json(todo);
  }

  // ... 他のメソッド
}
```

### ステータス完了切り替えロジック

```typescript
async toggleCompletion(id: string) {
  const todo = await this.findById(id);
  if (!todo) throw new NotFoundError('Todo not found');

  const newStatus = todo.status === 'completed' ? 'pending' : 'completed';
  const completedAt = newStatus === 'completed' ? new Date() : null;

  return this.update(id, {
    status: newStatus,
    completed_at: completedAt,
  });
}
```

## 学んだこと（Key Learnings）

### 上手くいった点
- 明確なAPI設計により実装がスムーズになった
- Zodによるバリデーションでエッジケースを早期に発見できた
- ページネーションによってパフォーマンスの問題を防げた
- Enum型を使用してデータ整合性を保つことができた

### 回避できたよくある落とし穴
- レスポンスの構造を常に一貫させること
- PATCHを使用した部分的な更新の正しい処理
- 外部キーと頻繁にフィルタされる列でのインデックス付け
- 複雑な操作にトランザクションを使用すること

### テスト戦略
- バリデーションロジックの単体テスト
- APIエンドポイントの統合テスト
- フィルタの組み合わせテスト
- ページネーションのエッジケースの検証
