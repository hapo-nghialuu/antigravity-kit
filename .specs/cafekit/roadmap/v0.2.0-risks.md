## P1 Risks (High Priority)

### Risk 1: Low Adoption (Users Don't Use v0.2.0)

**Description:**  
Users install v0.1.0 but don't upgrade to v0.2.0, or upgrade but don't use new features.

**Likelihood:** Medium  
**Impact:** High (wasted development effort, low ROI)  
**Risk Score:** 6

**Indicators:**
- <10% feature adoption by Day 28
- Users stick with v0.1.0 despite v0.2.0 available
- No mentions of new features in Slack

**Mitigation:**
1. **Pre-Launch (Day 11):** Validate features with users before development
2. **Beta Testing (Day 19):** Get early feedback, iterate if needed
3. **Marketing (Day 21):** Clear launch announcement with benefits
4. **Education:** Show examples of new features solving real problems
5. **Onboarding:** Update README with "Why upgrade to v0.2.0?"

**Contingency:**
- If adoption <30% by Day 28 → Conduct follow-up interviews to understand why
- Iterate on features in v0.2.1 patch

---

### Risk 2: Critical Bugs in Week 1

**Description:**  
v0.1.0 has critical bugs that block users, forcing emergency fixes and delaying v0.2.0 timeline.

**Likelihood:** Medium  
**Impact:** High (timeline delay, user frustration)  
**Risk Score:** 6

**Indicators:**
- >3 GitHub issues labeled "critical" or "blocker"
- Installation failure rate >20%
- Multiple Slack reports of same error

**Mitigation:**
1. **Pre-Launch Testing:** Test v0.1.0 thoroughly before publish
2. **Early Monitoring:** Check #cafekit-support every 2 hours on Day 1-2
3. **Fast Response:** Fix critical bugs within 24 hours
4. **Hotfix Process:** v0.1.1 patch release ready

**Contingency:**
- If >3 critical bugs by Day 5 → Delay v0.2.0 development to Day 16 (+1 day)
- If >5 critical bugs by Day 7 → Re-evaluate roadmap, focus on stability

---

### Risk 3: No Feedback (Low Survey Response)

**Description:**  
Survey response rate <60%, insufficient data to prioritize v0.2.0 features.

**Likelihood:** High  
**Impact:** Medium (guesswork instead of data-driven decisions)  
**Risk Score:** 6

**Indicators:**
- <6 survey responses by Day 5 evening
- No interview volunteers by Day 8
- Low engagement in #cafekit-support

**Mitigation:**
1. **Incentivize:** "Help shape v0.2.0 with your feedback!"
2. **Personal Touch:** DMs instead of mass emails
3. **Short Survey:** 2 minutes max, 6 questions only
4. **Follow-up:** Reminder DM on Day 5 afternoon
5. **Alternative Sources:** Use Slack conversations as qualitative data

**Contingency:**
- If <6 responses by Day 6 → Skip survey analysis, rely on interviews only
- If <3 interviews by Day 9 → Use Slack feedback + top pain points from limited data
- Focus on P0 features only (4.5h instead of 11h)

---

### Risk 4: Scope Creep (Users Request P2 Features)

**Description:**  
Users request features beyond P0+P1, pressure to include in v0.2.0 despite time constraints.

**Likelihood:** High  
**Impact:** Medium (timeline delay, feature overload)  
**Risk Score:** 6

**Indicators:**
- Survey shows >5 different feature requests
- Interviews reveal "must-have" features not in plan
- Team discussions about adding "just one more feature"

**Mitigation:**
1. **Clear Scope (Day 11):** Lock P0+P1 features publicly, communicate clearly
2. **Defer P2:** Explicitly list P2 features deferred to v0.3.0
3. **Stick to Plan:** Remind team/users of 3-week fast iteration goal
4. **Decision Framework:** Use decision-framework.md to evaluate new requests

**Contingency:**
- If pressure to add P2 features → Re-evaluate using decision framework
- If truly critical → Swap P1 feature for P2 feature (keep total effort ≤11h)
- If not critical → Defer to v0.3.0, communicate timeline

## P2 Risks (Medium Priority)

### Risk 5: Dev Overrun (>11h Effort)

**Description:**  
Development takes longer than 11h estimate, delays beta or release.

**Likelihood:** Medium  
**Impact:** Medium (timeline delay, rushed testing)  
**Risk Score:** 4

**Indicators:**
- Day 15 features not complete by EOD
- Unexpected technical challenges
- Implementation more complex than estimated

**Mitigation:**
1. **Buffer Time:** 30 min buffer each day (Days 15-17)
2. **Progressive Testing:** Test each feature immediately after implementation
3. **Simplify:** Cut complexity if feature takes >estimated time
4. **Daily Check:** End-of-day review, adjust next day plan

**Contingency:**
- If >2h over estimate by Day 16 → Cut P1 feature (config file or uninstall)
- If >4h over estimate by Day 17 → Ship P0 only (4.5h), defer P1 to v0.2.1

---

### Risk 6: Breaking Changes

**Description:**  
v0.2.0 introduces changes that break v0.1.0 users' workflows.

**Likelihood:** Low  
**Impact:** High (user frustration, trust loss)  
**Risk Score:** 3

**Indicators:**
- v0.2.0 changes existing command behavior
- File structure changes
- CLI flag conflicts

**Mitigation:**
1. **Backward Compatibility:** Maintain v0.1.0 behavior as default
2. **Additive Changes:** New features are opt-in (flags, config)
3. **Testing:** Test both v0.1.0 and v0.2.0 workflows
4. **Migration Guide:** Clear upgrade instructions

**Contingency:**
- If breaking change discovered in beta (Day 19) → Fix immediately (Day 20)
- If unfixable → Revert to v0.1.0, delay v0.2.0 release

---

### Risk 7: Platform-Specific Bugs

**Description:**  
Features work on one platform (Claude) but fail on another (Antigravity), or vice versa.

**Likelihood:** Medium  
**Impact:** Medium (partial user base affected)  
**Risk Score:** 4

**Indicators:**
- Bug reports from only Antigravity users or only Claude users
- Platform detection fails on specific setups
- Path handling differences (Windows vs macOS/Linux)

**Mitigation:**
1. **Test Both Platforms:** Test on both .agent/ and .claude/ projects
2. **Cross-Platform Testing:** Test on Windows, macOS, Linux
3. **Early Detection:** Beta testers use both platforms
4. **Verbose Mode:** --verbose helps debug platform-specific issues

**Contingency:**
- If platform-specific bug found → Fix in Day 20 (before release)
- If unfixable quickly → Document workaround, fix in v0.2.1

## P3 Risks (Low Priority)

### Risk 8: Beta Testers Don't Test (Day 19)

**Description:**  
v0.2.0-beta released but users don't test, no beta feedback collected.

**Likelihood:** Medium  
**Impact:** Low (miss minor bugs, but not critical)  
**Risk Score:** 2

**Mitigation:**
1. **Clear Ask:** Specific testing instructions, not just "try it"
2. **Easy Testing:** Provide test project template
3. **Reminders:** DM reminder on Day 19 evening
4. **Incentive:** "You'll get v0.2.0 features first!"

**Contingency:**
- If <5 users test by Day 19 EOD → Test internally (Nghia + 1-2 team members)
- Rely on own testing, release on Day 21 as planned

---

### Risk 9: Insufficient Interview Volunteers

**Description:**  
<3 users volunteer for interviews, insufficient qualitative data.

**Likelihood:** Low  
**Impact:** Medium (less depth in feedback)  
**Risk Score:** 2

**Mitigation:**
1. **Personal Invitations:** DM power users directly
2. **Easy Scheduling:** Offer multiple time slots
3. **Short Duration:** 30 min max
4. **Fallback:** Use survey open-ended responses

**Contingency:**
- If <3 volunteers → Conduct 2 interviews + rely on survey data
- If 0 volunteers → Skip interviews, use survey + Slack conversations

---

### Risk 10: Update Command Conflicts

**Description:**  
Update command causes conflicts (file version mismatch, backup failures).

**Likelihood:** Low  
**Impact:** Medium (users can't update smoothly)  
**Risk Score:** 2

**Mitigation:**
1. **Backup First:** Always backup before update
2. **Version Check:** Verify versions before proceeding
3. **Rollback:** Allow users to restore from backup
4. **Testing:** Test update flow thoroughly (v0.1 → v0.2)

**Contingency:**
- If update fails in beta → Fix on Day 20
- If unfixable → Document manual update process as workaround
