hapo:specs — Logic & Decision Flow

Entry — dispatch 4 flag

router
Bộ flag duy nhất

--auto · --validate · --status · --archive. Mọi quyết định khác (spec nào, mới/tiếp tục, dừng ở đâu) do hỏi tương tác, không qua flag. (alias ngầm: status/archive/resume)

Thứ tự dispatch
--status→ in bảng trạng thái → dừng.
--validate <feature>→ nhảy Step 9, cấm Step 1–8.
--archive→ archive workflow → dừng.
--auto→ chạy hết (tạo mới hoặc tiếp tục spec dở) tới Tasks, auto-approve, không hỏi.
không flag→ Interactive State Discovery (bên dưới).
Interactive State Discovery (không flag)
  • Quét specs/: có spec dở → hỏi Tiếp tục <spec> / Tạo mới; không có → tạo mới.
  • Tạo mới thiếu mô tả → xin mô tả + safety gate (clarity / brainstorm).
  • Creation Mode Gate: Auto (→Tasks) · Dừng sau Design · Từng bước có duyệt.
  • Tiếp tục spec dở → đọc current_phase → hỏi phase còn lại → chạy tiếp.
Lưu ý: đây chỉ là lớp gọi — pipeline Step 1–10, validator, templates, rules giữ nguyên. "Dừng sau Design" = chạy Step 1–6 rồi dừng trước Step 7.

Analyze Description

phân loại
Mục tiêu

Đánh giá độ rõ + độ phức tạp của yêu cầu, quyết định có đủ điều kiện làm spec hay phải hỏi/chuyển hướng.

Tiền xử lý bắt buộc (multimodal)
  • Đầu vào có .png/.jpg/.mp3/.mp4 → gọi hapo:ai-multimodal
  • .pdf→hapo:pdf · .docx→hapo:docx · .pptx→hapo:pptx · .xlsx/.csv→hapo:xlsx
  • Trích nội dung trước, nhập vào "description" đã làm giàu.
Quy tắc ra quyết định
< 20 từ / thiếu danh từ cụ thể→ STOP, hỏi 1–2 câu làm rõ.
≥ 2 kiến trúc khả thi · scope mơ hồ · 3+ subsystem · user muốn "explore/compare"→ STOP, chuyển /hapo:brainstorm trước khi tạo file.
Quá đơn giản (1 file, typo, config)→ cảnh báo "có thể không cần spec, vẫn tiếp tục?"
Rõ & non-trivial→ sang Step 2.
Điều kiện dừng: mơ hồ về output/acceptance/scope → không được "đoán" và tạo spec; phải hỏi hoặc brainstorm.

Cross-Spec Dependency Scan

quét
Mục tiêu

Tránh tạo spec trùng lặp hoặc xung đột với spec đang tồn tại.

Quy tắc ra quyết định
  • Quét specs/ → so sánh file chồng lấn, dependency chung, cùng vùng tính năng.
  • Phát hiện quan hệ → ghi 2 chiều vào spec.json.dependencies (blockedBy / blocks).
  • Trùng scope rõ rệt → cảnh báo "spec này có thể rebuild thứ đã có".
Đầu ra

spec.json.dependencies được cập nhật nếu có quan hệ.

5-Dimension Complexity Assessment + Scope Inquiry

gate
Mục tiêu

Chấm độ phức tạp đa chiều để không bỏ sót rủi ro, rồi chốt mức đầu tư (scope level) cùng user.

Skip khi

task hiển nhiên trivial (1 file/typo/config), mô tả <20 từ rõ ràng, hoặc user nói "just do it".

5 chiều đánh giá
ChiềuCâu hỏi cốt lõiKết quả rẽ nhánh
1. Semantic IntentÝ nghĩa nghiệp vụ? Hệ thống hiện hành xử thế nào?Trùng thứ đã có → cảnh báo
2. Implementation HypothesisCần model/API/tích hợp mới hay chỉ logic/UI cục bộ?Định hình tác động cấu trúc
3. Gap SizingKhoảng cách hiện trạng↔mục tiêuSmall / Medium / Large
4. Risk (Cynefin)Mức độ "biết được" lời giảiClear / Complicated / Complex / Chaotic
5. Blast RadiusHỏng thì lan tới đâu?Isolated / Moderate / Critical Path
Quy tắc ra quyết định (theo Risk & Blast)
Risk = Chaotic→ THOÁT spec, chuyển /hapo:hotfix (ổn định trước).
Risk = Complex→ bắt buộc thêm task spike/prototype (time-box ≤ 4h, go/no-go).
Risk = Complicated→ lên kế hoạch kỹ, có thể cần researcher subagent.
Blast = Critical Path→ spec BẮT BUỘC có rollback strategy + test coverage trong task files.
Clear + Isolated→ tiến hành tự tin.
Scope Inquiry (hỏi user — bất biến sau khi chốt)
Lựa chọnÝ nghĩaHệ quả
ExpandResearch sâu, nhiều hướng, thêm stretch featuresNhiều task hơn
HoldGiữ scope như mô tả, ưu tiên chất lượngTập trung edge case, test
ReduceChỉ lõi, hoãn mọi thứ không thiết yếuÍt task, kiến trúc đơn giản
Immutable Rule: user chọn xong → tôn trọng suốt workflow. Không tự ý phình khi chọn Reduce, không tự ý co khi chọn Expand/Hold. Ghi vào spec.json.scope_lock.

Init

tạo file
Quy tắc ra quyết định
  • Glob kiểm tra trùng slug trong specs/ trước khi tạo.
  • Tạo specs/<feature>/ + sinh spec.json từ template (tên output luôn là spec.json, không phải tên template).
  • Khởi tạo scope_lock: source (mô tả gốc), in_scope, out_of_scope, expansion_policy: requires-user-approval.
  • Tạo requirements.md rỗng từ template init.
Quan trọng: Step 4 chỉ khởi tạo file. Trong run end-to-end → tự động sang Step 5. Chỉ dừng nếu user yêu cầu "init only".

5

Evidence Gate + Requirements + Research

gate quan trọng nhất
Mục tiêu

Chống "design từ trí nhớ". Thu thập bằng chứng → viết requirements chuẩn EARS có thể kiểm thử.

Phân loại nhu cầu bằng chứng (quyết định scout/research)
Loại bằng chứngBẮT BUỘC khi…
Codebase scout (targeted)đổi hành vi cũ; chạm API/CLI/export/schema/auth/session/permission/config/hook/runtime; thiếu path; có thể vỡ test; resume spec cũ; cross-package/runtime.
External researchphụ thuộc third-party API/lib/platform policy/AI provider; quy tắc security/auth/payment/privacy/delete-data; chuẩn perf/a11y/SEO; user nói "best/optimal/latest/recommended".
Skip (ghi rationale)sửa 1 file trivial; đổi text/docs nội bộ; file mới cô lập không tích hợp; đã có report user cung cấp gần đây.
Quy tắc viết requirements
  • Viết research.md trước requirements — phải có ## Evidence Summary: scout result, research/skip rationale, quyết định chọn, phương án bị loại, gaps, hệ quả task/test.
  • Requirements theo EARS (When / While / If / Where / The system shall), mỗi cái có ID số.
  • Đo lường được: thay "fast/safe" bằng ngưỡng cụ thể ("<500ms", "HTTP 400", "≥80% coverage").
  • Mỗi requirement: Singular · Unambiguous · Testable · numeric ID. Gồm cả NFR (Performance, Security, Scalability, Reliability, Accessibility).
Nhánh dừng
Evidence gap sau khi đã research→ hỏi user: "tiếp tục với rủi ro / scout thêm / thu hẹp scope".
Bằng chứng lộ ra hướng chưa rõ / nhiều phương án ngang nhau→ chuyển /hapo:brainstorm.

Bước 7b — Task Scoring Rubric (chấm 0–3 mỗi chiều → quyết định)

8 chiều: Dependency criticality · Implementation risk · Blast radius · User value · Evidence confidence · Testability · File conflict · Scope creep.

Tổng điểmPriorityHành động
0–6P3giữ gọn, merge nếu không có proof độc lập
7–12P2task thường, ghi rõ deps + evidence
13–18P1cân nhắc split, evidence mạnh hơn
19+P1 criticalsplit hoặc thêm spike; không (P) trừ khi file tách biệt
Mandatory overrides
Scope creep = 3→ STOP, AskUserQuestion trước khi tạo task.
Evidence=3 & Risk≥2→ tạo spike task trước.
Blast=3→ Evidence phải có rollback + negative-path proof.
File conflict ≥2→ bỏ marker (P) trừ khi ownership tách bạch.
Quy tắc cấu trúc & phủ requirement
  • Tên: tasks/task-R{N}-{SEQ}-<slug>.md (SEQ 2 chữ số). R0=foundation, R1+=feature.
  • Mỗi task self-contained 8 mục: Context · Constraints · Steps · Requirements · Related Files · Completion Criteria · Evidence · Risk Assessment.
  • Mọi requirement ID phải xuất hiện ≥1 task — thiếu = fail.
  • Legacy Protection: test/file sẽ vỡ (theo Blast Radius) → tạo task sửa rõ ràng, không để ngoài scope.
  • Dựng spec.json.task_registry: mỗi task có id, title, status, dependencies, blocker, timestamps.

tùy chọn

Finalization Audit + Completion

hard gate
Quy tắc ra quyết định (audit FAIL nếu…)
  • Rebuild task_files & task_registry từ filesystem thật.
  • Task trên đĩa thiếu trong registry/files — hoặc ngược lại.
  • Tên task sai regex task-R{N}-{SEQ} 2 chữ số.
  • Spec non-trivial thiếu Evidence Summary trong research.md.
  • Requirement/NFR dùng nhãn không phải số (NFR-1, SEC-1…).
  • Task thiếu Completion Criteria / Evidence.
  • Output runtime nhưng không chứng minh reachability / không có integration task.
  • Provider đã đổi khỏi Anthropic nhưng còn chuỗi cũ (Claude API, Haiku…) ngoài research.md.
  • Privacy/delete-data trộn nhiều policy (phải chọn 1 canonical).
Đầu ra (chỉ khi audit + validator pass)

Set progress.tasks = "done" + ready_for_implementation = true → in block:

✅ Spec complete: specs/<feature>/
📌 Next step → /hapo:develop <feature>
💡 Tip: chạy /clear trước khi implement.

State Machine 2 lớp (Tollgate Protocol)

⚙️ Machine Layer — spec.json

  • phase / current_phase (init→requirements→design→tasks→develop→test→review)
  • progress.* trạng thái từng phase
  • task_registry: status, dependencies, started/completed/last_updated
  • approvals + ready_for_implementation
  • scope_lock (bất biến sau xác nhận)
⇄

👤 Human Layer — tasks/task-R*.md

  • Checkbox [ ]/[x] tiến độ chi tiết
  • Completion Criteria (định nghĩa "done")
  • Evidence (bằng chứng verify thực tế)
  • Status: pending / in_progress / blocked / done
Sync-back Rule: hoàn thành/blocked KHÔNG được chỉ trả lời "Done" trong chat. Phải cập nhật cả 2 lớp trước khi trả quyền. Hook spec-state.cjs liên tục enforce. Golden rule: không mark done trước khi có execution proof; registry không được lệch với markdown.

Hard gate: ready_for_implementation = true

Chỉ true khi THỎA tất cả:

  • ✔ approvals.requirements.approved = true
  • ✔ approvals.design.approved = true
  • ✔ approvals.tasks.approved = true
  • ✔ progress.tasks = "done"
  • ✔ task_files khớp filesystem
  • ✔ task_registry khớp filesystem, không thiếu task
  • ✔ nếu validation_recommended = true → validation.status = "completed" (hoặc rủi ro được user chấp nhận có ghi nhận)
  • ✔ validator exit 0
Đặc biệt: spec ≥ 5 task → ready_for_implementation giữ false cho tới khi --validate chạy xong Red Team + Validate và ghi validation.status = "completed".
